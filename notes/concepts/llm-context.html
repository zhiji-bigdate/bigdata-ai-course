学习资料大模型的上下文（LLM Context）

1. 概念地图（Concept Map）

LLM 工作机制 ├── 输入：Prompt = 你的问题 + 上下文 ├── 处理：所有 token 一起进入 Transformer │ → 每读一个 token 都要「回头看」所有之前的 token │ → 注意力机制是核心 └── 输出：根据整个上下文预测下一个 token ↑ 上下文 = 这条对话的全部历史 + 你塞进 prompt 的所有东西 上下文窗口（Context Window）= 模型一次能"装下"的最大 token 数

一句话定位：上下文就是模型当下能看到的所有文字，它决定了模型这一轮能"记住"什么、"引用"什么。

2. 一句话定义

大模型的上下文（Context）= 当前对话中模型能直接"看到"的所有 token（系统提示 + 你的历史消息 + 你上传的文件等），是模型这一轮回答时唯一的信息来源。

3. 分层理解（Layered Explanation）

直观类比（Intuition）

把大模型想象成一个只有短期记忆的聪明人。

  • 让他回答问题前，你得把背景材料贴给他（"上下文"）。
  • 他的"短期记忆"就是上下文窗口——一张固定的桌子，材料放不下就放不进来。
  • 你不贴上去的东西，他永远不会知道——他不能去查你电脑、不能记起上周说过的话（除非你再贴一次）。

所以：和 LLM 交流的工程核心任务，就是精心挑选要放上桌子的内容。多了浪费、少了他又答不好。

机制原理（Mechanism）

Token 是什么：模型不是按"字"读，是按"token"读。中文一个字 ≈ 1–2 个 token，英文一个单词 ≈ 1–3 个 token。GPT-4 一个上下文窗口大概是 8K / 32K / 128K token。

模型怎么用上下文：

  • 每生成一个新 token，模型会回头看整个上下文（不是只看最新一句），通过"注意力"机制决定哪些旧 token 更重要。
  • 这就是为什么模型能"引用"5 句之前的对话。
  • 但注意力是有损的——窗口越大，越前面的内容越容易被"稀释"（lost in the middle 现象）。

关键约束：

约束含义影响
上下文窗口大小模型一次能读多少 token超过的会被截断
计费输入 token 都要花钱塞太多浪费钱
延迟上下文越长推理越慢100K 上下文比 1K 慢 10 倍+
失真长上下文中部信息容易被忽略重要信息放首尾

边界与误区（Boundaries）

  • ❌ 误区 1：「模型能记住我以前聊过什么」
    默认不能。每次新对话，模型都是从零开始。要"记住"，要么把历史粘回去，要么用 RAG，要么用外置记忆系统。
  • ❌ 误区 2：「上下文窗口越大越好」
    越大意味着慢、贵、还容易丢信息。很多场景下精心挑选 4K 比粗放塞 100K 效果更好。
  • ❌ 误区 3：「上下文 = 知识」
    上下文是信息，知识在模型权重里。一个事实可以同时在两处，模型也可能答错已写进上下文的内容（"读到不等于用对"）。
  • ✅ 边界：上下文是这一次对话的临时工作区，关掉就没了。它不是数据库，别拿它存东西。

4. 正反例（Examples）

✅ 好例子：带着关键信息提问

你：以下是我的代码（粘 200 行）。
    我要加一个缓存功能，但只在用户登录后启用。
    请帮我写一个最简的方案。

为什么好：关键背景、约束、目标全在上下文里，模型能直接给方案。

❌ 坏例子：让模型"自己查"

你：我代码里有个 bug，帮我修。

为什么坏：上下文里没有代码。模型要么瞎猜，要么只能给通用建议。

金科玉律：和 LLM 沟通 80% 的功夫，是把模型答好问题所需的全部信息塞进上下文。

5. 自检问题（Self-Check）

1. 上下文窗口是越大越好吗？

不是。越大意味着慢、贵、还容易"失焦"（lost in the middle）。应根据任务精度需求精选内容塞进去，而不是无脑堆。

2. 模型真的"记住"我们的对话历史吗？

默认不记。每次新会话，模型从零开始。历史消息是被作为上下文重新喂回去的，不是它自己"想起来的"。一旦新会话开始，旧的就丢了。

3. 如果一段长文档塞不进上下文怎么办？

常见三种解法：(1) 截断——只读前 N 行；(2) 摘要——先让模型压缩成长摘要再读；(3) RAG——把文档切片存到向量库，按需检索最相关的片段塞进上下文。
