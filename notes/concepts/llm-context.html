学习资料大模型的上下文（LLM Context）

1. 学习目标（Learning Objectives）

学完这份资料，你将能够：

  • 用一句话说出"上下文"是什么
  • 解释 上下文窗口（Context Window）的工作机制
  • 区分 上下文、知识、记忆三者的关系
  • 应用 上下文工程的基本原则来提问
  • 识别 关于上下文的 3 个最常见误区

2. 核心问题（Driving Questions）

  • 上下文窗口是越大越好吗？
  • 大模型真的"记住"了我们之间的对话吗？
  • 为什么长文档喂给 LLM 后，它会"忘记中间"？
  • 当文档塞不进上下文时，工程上有哪些解决方案？

3. 概念地图（Concept Map）

LLM 工作机制 ├── 输入：Prompt = 你的问题 + 上下文 ├── 处理：所有 token 一起进入 Transformer │ → 每读一个 token 都要「回头看」所有之前的 token │ → 注意力机制是核心 └── 输出：根据整个上下文预测下一个 token ↑ 上下文 = 这条对话的全部历史 + 你塞进 prompt 的所有东西 上下文窗口（Context Window）= 模型一次能"装下"的最大 token 数

一句话定位：上下文就是模型当下能看到的所有文字，它决定了模型这一轮能"记住"什么、"引用"什么。

4. 结构化解释（Structured Explanation）

4.1 一句话定义

大模型的上下文（Context）= 当前对话中模型能直接"看到"的所有 token（系统提示 + 你的历史消息 + 你上传的文件等），是模型这一轮回答时唯一的信息来源。

4.2 直观类比（Intuition）

把大模型想象成一个只有短期记忆的聪明人。

  • 让他回答问题前，你得把背景材料贴给他（"上下文"）。
  • 他的"短期记忆"就是上下文窗口——一张固定的桌子，材料放不下就放不进来。
  • 你不贴上去的东西，他永远不会知道——他不能去查你电脑、不能记起上周说过的话（除非你再贴一次）。

所以：和 LLM 交流的工程核心任务，就是精心挑选要放上桌子的内容。多了浪费、少了他又答不好。

4.3 机制原理（Mechanism）

Token 是什么：模型不是按"字"读，是按"token"读。中文一个字 ≈ 1–2 个 token，英文一个单词 ≈ 1–3 个 token。GPT-4 一个上下文窗口大概是 8K / 32K / 128K token。

模型怎么用上下文：

  • 每生成一个新 token，模型会回头看整个上下文（不是只看最新一句），通过"注意力"机制决定哪些旧 token 更重要。
  • 这就是为什么模型能"引用"5 句之前的对话。
  • 但注意力是有损的——窗口越大，越前面的内容越容易被"稀释"（lost in the middle 现象）。

关键约束：

约束含义影响
上下文窗口大小模型一次能读多少 token超过的会被截断
计费输入 token 都要花钱塞太多浪费钱
延迟上下文越长推理越慢100K 上下文比 1K 慢 10 倍+
失真长上下文中部信息容易被忽略重要信息放首尾

4.4 边界与误区（Boundaries）

  • ❌ 误区 1：「模型能记住我以前聊过什么」
    默认不能。每次新对话，模型都是从零开始。要"记住"，要么把历史粘回去，要么用 RAG，要么用外置记忆系统。
  • ❌ 误区 2：「上下文窗口越大越好」
    越大意味着慢、贵、还容易丢信息。很多场景下精心挑选 4K 比粗放塞 100K 效果更好。
  • ❌ 误区 3：「上下文 = 知识」
    上下文是信息，知识在模型权重里。一个事实可以同时在两处，模型也可能答错已写进上下文的内容（"读到不等于用对"）。
  • ❌ 误区 4：「只要放进 prompt，模型就一定会用」
    注意力是有损且不均匀的。模型可能"看到"但没"用对"。重要信息需要显式强调、放在首尾。
  • ✅ 边界：上下文是这一次对话的临时工作区，关掉就没了。它不是数据库，别拿它存东西。

5. 应用案例（Application Cases）

案例 1：Cursor / Copilot 的代码补全（真实场景）

当你用 Cursor 编辑 Python 代码时，它把你"当前文件 + 引用文件 + 光标前 N 行"一起塞进上下文，模型据此补全下一行。

上下文工程的真实商业场景：上下文装什么、装多少，直接决定产品体验。

案例 2：动手做一个"上下文裁剪"小工具（课堂练习）

任务：写一个 Python 脚本 truncate.py，把一段长文本按 token 数截断。

import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
def truncate_to_tokens(text, max_tokens=2000):
    tokens = enc.encode(text)
    if len(tokens) <= max_tokens:
        return text
    return enc.decode(tokens[:max_tokens])

跑一下，亲身感受"2000 token 大概能装多少字"。

6. 概念辨析（Concept Disambiguation）

概念本质核心区别
上下文 vs 知识信息 vs 权重上下文是这一轮临时给的，知识是预训练烧进模型的
上下文 vs 记忆输入 vs 状态上下文是当前输入，记忆是跨会话持久化
上下文窗口 vs 上下文工程容量 vs 策略窗口是上限，工程是怎么塞
RAG vs 长上下文检索 vs 暴力RAG 按需取，长上下文全塞

最容易混的一对：上下文 vs 知识

同一个事实，可以同时在训练数据（→ 知识，存进权重）和当前 prompt（→ 上下文，输入给模型）两处。但更新成本完全不同：改知识要重新训练（百万美元级），改上下文只要改 prompt（零成本）。

7. 自检问题（Self-Check）

1. 上下文窗口是越大越好吗？

不是。越大意味着慢、贵、还容易"失焦"（lost in the middle）。应根据任务精度需求精选内容塞进去，而不是无脑堆。

2. 模型真的"记住"我们的对话历史吗？

默认不记。每次新会话，模型从零开始。历史消息是被作为上下文重新喂回去的，不是它自己"想起来的"。一旦新会话开始，旧的就丢了。

3. 如果一段长文档塞不进上下文怎么办？

常见三种解法：(1) 截断——只读前 N 行；(2) 摘要——先让模型压缩成长摘要再读；(3) RAG——把文档切片存到向量库，按需检索最相关的片段塞进上下文。
